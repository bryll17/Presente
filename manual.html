PRESENTE — Owner's Manual & Recovery Guide

v3.1 kit · Keep this file with your master ZIP · Print a copy and fill in Section 1 by hand

Read this first

This manual assumes the worst: the person who built this app is gone, the chat that created it is gone, and something just broke. Everything you need to diagnose, repair, or completely rebuild Presente is in this document plus the master ZIP (the 14-file kit this manual shipped with). As long as you have the ZIP, a Google account, and a GitHub account, the whole system can be rebuilt from nothing in about 30 minutes.

The one rule that makes everything else recoverable: keep the master ZIP and your weekly backup files in at least two places (for example: your personal Google Drive AND a USB drive or laptop). Every recovery drill below starts from those files.

3. Troubleshooting — find your symptom

The app itself

IF the app won't open / blank page / spinning: check the device's internet, then force-close and reopen. Still stuck: open the app link in a normal browser tab and hard-refresh (pull down, or Ctrl+Shift+R on a computer). Still stuck: on GitHub, repo → Settings → Pages — confirm it still says "Your site is live". Still stuck: re-upload all 12 web files from the master ZIP to the repo (Drill D, step 2 onward).
IF you see a 404 "File not found": the file at that address is missing or misnamed. The app must exist as index.html at the top level of the repository — check the repo file list. Re-upload from the ZIP if needed.
IF you see a red "Preview mode" banner: you opened the raw file instead of your hosted link. Close it and open your real app link (Section 1).
IF the app feels slow or complains about storage: your yearly archive is overdue. Do the end-of-year ritual (Section 5) even mid-year if needed — export, backup, archive, reconnect a fresh Sheet.

Scanning

IF the camera won't start: the browser was denied permission. iPhone/iPad: Settings app → Safari (or the site's settings) → Camera → Allow; if launched from the home-screen icon, delete the icon, open the link in Safari, allow camera, re-add to Home Screen. Android: Chrome → ⋮ → Settings → Site settings → Camera. Meanwhile, Photo mode always works: it snaps a picture and decodes it.
IF a QR won't scan: more light, hold steady, fill the frame. A damaged card: reprint from Export → Print QR cards, or send the student their PNG (▣ button → Save PNG).
IF scanning says "Student not in roster": that student was removed from all classes. Re-add them (this creates a NEW code — reprint their card), or if the removal was a mistake, restore your latest backup.

Sync

IF the header says "sync off": this device never got the URL + token. Settings → paste both → Save → Sync now.
IF the dot is red ("sync error"): read the message under Settings → Sync. In order: (1) internet working? (2) URL and token exactly right — retype the token, watch for spaces; (3) run the gate test: open YOUR-EXEC-URL?chk=test in a private browser window — you should see a short {"ok":false...} line. A Google login page instead means the deployment access isn't "Anyone" (or an org admin changed policy): redeploy via Apps Script → Deploy → Manage deployments → pencil → check settings → New version.
IF marks are missing on the other device: both devices online → Sync now on both. The truth lives in the Sheet's Events tab — open it on a computer; if the marks are THERE, the lagging device just needs a sync; if they're NOT there, the originating device hasn't synced — open it online.
IF the two devices show different rosters: whichever device has the CORRECT roster: make any tiny edit (rename a class and rename it back) → Sync now on it, then Sync now on the other. Latest roster edit wins.

Emails

IF confirmation emails don't arrive: in order: (1) the student has an email saved (✎ edit shows it)? (2) SEND_EMAILS = true in the script, saved, AND republished (Manage deployments → New version)? (3) recipient checked spam? (4) quota: ~100 recipients/day on a personal Gmail-account Sheet, 1,500/day on a Workspace-account Sheet — once exhausted, mail silently resumes the next day; (5) emails only send for Present/Late marks made by scan or tap — never for the auto-Absent sweep or online self check-ins (the check-in page itself is the confirmation).

Online check-in links

IF students say the link doesn't work: (1) expired — links die at the deadline by design; make a new one. (2) "Link not recognized" — the link got mangled in chat; re-copy and resend the whole thing. (3) A Google login appears for students — org policy changed; run the gate test above. (4) A 404 — checkin.html is missing from the repo; upload it from the ZIP.
IF a student is marked whom you doubt was present: open Records — self check-ins are labeled and timestamped to the second; the Sessions tab in the Sheet shows exactly which code checked in when. Codes are per-student: someone used that student's own QR/code.

Exports

IF CSV/PDF/Word buttons do nothing: the browser is blocking downloads or pop-ups for the site — allow them in site settings, or try from the other device. PDF falls back to a print dialog if its library is missing: choose "Save as PDF" there.

4. Recovery drills

Drill A — a device is lost, broken, or wiped (5 minutes)

  1. On the new/replacement device, open your app link → Add to Home Screen.
  2. Settings → paste the /exec URL + token → Save → Sync now.
  3. Everything returns: roster and full history pull from the Sheet. Verify a Records date, then resume.

Drill B — a device's data was accidentally erased but the device works

Same as Drill A. Only if the Sheet is ALSO gone do you need a backup file: Export tab → Restore backup → pick your newest presente-backup-*.json (check your computer's auto-backup folder — it holds dated copies) → then Drill C step 4.

Drill C — the Google side is gone (account closed, Sheet deleted, org account lost)

  1. Don't panic: your devices still hold everything locally and work offline.
  2. Under any Google account you control: sheet.new → Extensions → Apps Script → paste sync-script.gs from the ZIP → set a token → Deploy → New deployment → Web app → Execute as Me / Anyone → copy the new /exec URL. Run the gate test.
  3. If your devices were wiped too: first Restore backup from your newest backup file on one device.
  4. On the device with the most complete data: Settings → paste the NEW URL + token → Save → then press "Re-send everything to the Sheet". Watch the header dot until green — the entire history uploads (it auto-continues in batches).
  5. On the second device: paste the same URL + token → Sync now → then also press Re-send everything (this contributes any marks unique to that device; duplicates are ignored automatically).
  6. Update Section 1 of your printed manual with the new URL. If you moved off a Workspace account, remember the email quota drops to ~100/day.

Drill D — the GitHub side is gone (account or repo lost)

  1. Your data is untouched — it lives on devices and in the Sheet. Only the app's home is gone.
  2. On any GitHub account: create a repository → upload the 12 web files from the master ZIP → Settings → Pages → Deploy from branch main → wait → open the new link.
  3. On both devices: delete the old home-screen icon, open the new link, Add to Home Screen, and reconnect Settings (URL + token are unchanged — they belong to the Sheet, not GitHub).

Drill E — an update broke something; go back to a working version

Two ways, either works:

  • Master ZIP method (simplest): re-upload the file(s) from the ZIP over the broken ones. The ZIP is your certified-working version.
  • GitHub history method: in the repo, click the broken file → History (clock icon) → pick an older commit → view the file there → Download raw file (or copy its contents) → upload/commit it back. GitHub keeps every version of every file forever.

6. Rebuild from absolute zero (nothing exists but the ZIP)

  1. App: github.com → sign up → New repository (public) → upload the 12 web files from the ZIP → Settings → Pages → Deploy from a branch → main → save → wait 2 min → open https://USERNAME.github.io/REPONAME/.
  2. Backend: sheet.new → Extensions → Apps Script → paste sync-script.gs → set TOKEN (and SEND_EMAILS = true if wanted) → Save → Deploy → New deployment → Web app → Execute as Me / Access: Anyone → authorize → copy /exec URL → gate test (?chk=test in a private window must NOT show a login page).
  3. Devices: open the link on each → Add to Home Screen → Settings → URL + token → Sync now.
  4. Data: fresh start: build the roster (Roster tab → Bulk add) and print QR cards. Restoring old data: Export → Restore backup with your newest backup file, then Settings → Re-send everything to the Sheet.

7. Getting help in the future

This system was built in a private AI conversation that no longer exists and cannot be looked up — no future assistant remembers it. That's fine, because it was designed to be picked up cold:

  • Any web developer can maintain it from the ZIP: it's one plain HTML/JavaScript app, one small Google Apps Script, no accounts, no framework, no server of anyone else's.
  • To get AI help again: start a new conversation, attach index.html, sync-script.gs, and this manual, and say: "This is a QR attendance app I own — app on GitHub Pages, data synced via this Apps Script to my Google Sheet. Here's my problem: …" Those three files contain everything needed to understand and safely modify the system.
  • Before letting ANYONE (human or AI) change it: Download backup first, and keep the master ZIP untouched as your way back (Drill E).

Facts a helper will ask for

  • Data lives in the Sheet as: Events (one row per mark: uid, timestamps, date, class, student, status P/L/A/E, via scan/tap/auto/self), Roster (classId, className, studentId, name, number, email), Sessions (online check-in keys and expiries), Meta (roster version).
  • QR cards encode P1|classId|studentId; scanning finds the student in whatever class they're in now, so cards survive transfers.
  • The token gates all reading/writing except the student check-in endpoint, which accepts only a short-lived session key and can only mark a listed student Present during its window.
  • Conflict rule everywhere: latest change wins. Server ignores duplicate uids, which is why Re-send everything is always safe.
